# 准确率 95% → 82% 的根因：**权重和偏置来自两套不同的导出**（不是池化的问题）

日期：2026-10-17
结论：**已定位，并做到逐张复现（板级 200 张预测 100% 一致）**

---

## 一、结论先看

| 问题 | 严重度 | 一句话 |
|---|---|---|
| **① 权重走 ROM（`py/` 那套旧权重），偏置走 C 头文件（板级那套新权重）** | **主因，−9~14 pp** | 两条路分开生成，从来没有配套过 |
| ② 最后一层 OUT 也做 `>>>8` + int8 饱和 | −3.5~6 pp | OUT 只用来看 argmax，尺度无关，却被饱和截断 |
| ③ 训练用 max 池化，黄金模型用平均池化 | 口径不一致 | 而且固定 `shift=8`、无激活标定，所以池化一动准确率就跳 |
| ④ 之前的"平均池化 70%" | — | 是**除 2 而不是除 4**（`s>>1`），不是平均池化本身错 |

**板级实测 82%（`py/batch_result.csv`，200 张）在整数流水线里被精确复现：**
把"ROM 里的权重 + C 头文件里的偏置"喂进 bit-accurate 模型，前 200 张的预测
**逐张等于板子回传的结果（164/200，200/200 一致）**。换成配套的权重+偏置，
同一条流水线立刻回到 91%（max 池化）/ 96.5%（平均池化）。

### 2.2 硬件 ROM 里装的就是 `py/` 那套

Vivado 的 ROM IP `rom_all_tap` 初始化文件是 `../../../py/rom_all_tap.coe`
（见 `ip/rom_all_tap/rom_all_tap.xci`），综合实际读的是 `ip/rom_all_tap/rom_all_tap.mif`。

```
mif(11060)  vs  py/rom_all_tap.coe                       不同 = 0
mif(11060)  vs  仓库根 rom_all_tap.coe                   不同 = 0
mif(11060)  vs  prj/.../mem_init_files/rom_all_tap.coe   不同 = 0
```

按 tap 顺序还原成权重后，与两套头文件比：

| 层 | 与 `py/` 权重不符 | 与板级权重不符 |
|---|---:|---:|
| c1 | **0** / 42 | 42 / 42 |
| c3 | **0** / 608 | 608 / 608 |
| c5 | **0** / 7680 | 7680 / 7680 |
| f6 | **0** / 2520 | 2520 / 2520 |
| out | **0** / 210 | 210 / 210 |

**ROM = `py/` 那套（逐字全等）；板级 C 代码 = 另一套。**
而 `cnn_top.v` 已经不再接收 CPU 写的权重（`cnn_layer` 没有 `w` 参数），
权重只能来自 ROM，偏置仍然由 `cnn_load_bias()` 从 C 头文件写进 `CNN_BIAS`。
→ 一次推理里，权重是 A 模型的，偏置是 B 模型的。

### 2.3 完整矩阵（前 200 张 MNIST test，整数流水线，bit-accurate）

| 权重来源 | 偏置来源 | 池化 | 前100 | 前200 |
|---|---|---|---:|---:|
| **ROM（py/ 旧）** | **C 头文件（板级）** | **max** | **82.0%** | **82.0%** | ← **实机现在就是这一行** |
| ROM（py/ 旧） | C 头文件（板级） | avg | 92.0% | 91.5% |
| ROM（py/ 旧） | py/ 旧 | max | 87.0% | 86.0% |
| ROM（py/ 旧） | py/ 旧 | avg | 94.0% | 94.5% |
| C 头文件（板级） | C 头文件（板级） | max | 90.0% | 91.0% |
| **C 头文件（板级）** | **C 头文件（板级）** | **avg** | **97.0%** | **96.5%** | ← 口径一致 + 平均池化 |
| C 头文件（板级） | py/ 旧 | max | 91.0% | 91.5% |

板级实测 `py/batch_result.csv`：**164/200 = 82.0%**，与第一行**逐张完全一致（0 张不同）**。
这就是"Python 参考 95%、上板 80%"的来源——不是池化规则，是权重和偏置不是同一个模型。

### 2.4 "之前的 70%"是什么

同一套（不配套的）权重+偏置，只改硬件池化的除法：

| 池化实现 | 前100 | 前200 |
|---|---:|---:|
| 2×2 max | 82.0% | 82.0% |
| 2×2 平均 `(x0+x1+x2+x3)>>2` | 92.0% | 91.5% |
| **`(x0+x1+x2+x3)>>1`（除 2）** | **70.0%** | 73.0% |
| `(x0+x1+x2+x3)`（不除） | 34.0% | 34.5% |

你在 100 张上量的"70%"和 `>>1` 完全对上——**当时的平均池化实现除错了（除 2 而不是除 4）**，
不是"平均池化这个规则不对"。所以从 avg 换到 max 只是把 70% 换成了 82%，
真正的病根一直没被碰到。

### 2.5 为什么"池化一动准确率就跳"

因为这套量化**完全没有激活标定**：每层固定 `shift=8`，`s_y = s_x·s_w·256`。
max 池化让激活值整体变大，直接撞上 int8 的 127 天花板：

| 层 | max 池化 上饱和(≥127) 占比 | avg 池化 |
|---|---:|---:|
| C1 | 9.34% | 9.34% |
| S2 | 15.78% | 3.80% |
| C3 | 10.56% | 8.49% |
| **S4** | **22.38%** | 0.98% |
| C5 | 17.97% | 8.46% |
| F6 | 20.81% | 17.08% |
| OUT | 9.80% | 10.20% |

S4 有近 1/4 的值被削平。**是标定不准放大了池化的影响**，不是池化规则本身好或坏。

### 2.6 OUT 层的饱和单独扣分

- OUT 层 `shift=8` 后，200 张里有 **14 张**出现 ≥2 个 logit 同时被截断到 127；
  **7 张**的 argmax 因此被改变。
- 最后一层只取 argmax，尺度不影响结果，却白白损失了 3.5~6 pp。

## 三、修复步骤（按性价比排序）

### 修复 1（必须做，主因）：重新生成权重 ROM，让它和 C 头文件配套

```bash
cd python/golden
python export_wbase_tap.py          # 生成 rom_all_tap.hex（11066 字，含 Sobel）
```

这个文件已经和板级头文件 `LeNet_hw/include/lenet_weights_hw.h` **逐字一致（0 不符）**，
`wbase_tap.h` 的基地址也一致（0/42/650/8330/10850，Sobel 11060）。

关键：**综合读的是 ROM IP 的初始化文件（`.mif`/`.coe`），不是 `.hex`**。
所以必须把新内容做成 `.coe` 并**重新生成 `rom_all_tap` 这个 IP**（rebuild / regenerate），
否则 `.mif` 里还是旧数据。预期：82% → **91%**（max 池化）。

> 顺带纠正文档里的一个说法：`2026-10-16_加餐4` 附录写的"把 `.hex` 同步到 `rtl\cnn\`"
> 对**当前** RTL 无效——`cnn_top.v` 走的是 IP，没有 `$readmemh`；
> 而且当前 `.mif` 只有 11060 字，**没有 Sobel 段**，照现在的仓库状态重新综合，Sobel 会输出全 0。

### 修复 2（一行软件改动，白拿 3.5~6 pp）：最后一层的 shift 改成 10~12

```c
/* main.c：OUT 层最后一个参数 shift 从 QUANT_SHIFT(8) 改成 10 或 12，relu 仍为 0 */
cnn_layer(1, 1, 84, 1, 10, 1, 0, 10, 0, hw_x, out_bias, hw_y, 10);
```

最后一层只用来 argmax，**尺度不影响结果**，shift 只是"分辨率 vs 饱和"的取舍：

| 池化 | OUT shift | int8 饱和 | 前100 | 前200 |
|---|---|---:|---:|---:|
| max | 8 | 是 | 90.0% | 91.0% |
| max | **10 / 12** | 是 | **93.0%** | **94.5%** |
| max | 16 | 是 | 72.0% | 71.0% |（分辨率不够了）|
| max | 8 | 否（加宽输出） | 93.0% | 94.5% |
| avg | 8 | 是 | 97.0% | 96.5% |
| avg | **10 / 12** | 是 | **99.0%** | **98.5%** |

改动只需同步 Python 黄金模型的 OUT 层，便于逐层比对。

### 修复 3（口径统一）：池化规则训练/推理必须一致

- 训练：`py/main.py` 用 `F.max_pool2d`
- 黄金模型：`python/golden/lenet_golden.py` 用 **平均池化** ← 不一致

二选一，不能各写各的。注意：**实测平均池化数字更高（96.5~98.5%）是"标定不准"的副作用**
（它把激活值压小、避开了饱和），不是平均池化更正确；
单看训练语义，max 池化才是对的（91%→94.5%）。

### 修复 4（根治，可选）：做逐层激活标定

固定 `shift=8` + `s_y = s_x·s_w·256` 是这套方案最大的隐患。
正规做法（PTQ）：用浮点模型在若干张标定图上统计每层激活范围，
按范围反推每层的 shift，并同步重算下一层 `b_int = round(b/(s_x·s_w))`。
做完之后 max 池化应该能到 97%+，也不必再靠"换成平均池化"凑分。

### 防复发

新增 `python/golden/check_rom_consistency.py`，**每次综合前跑一遍**：

```bash
python python/golden/check_rom_consistency.py
```

它会检查三份头文件是否同源 + ROM 的 4 个副本是否等于板级头文件按 tap 顺序打包的结果，
不一致就退码 1。当前状态（修复前）输出：

```
IP rom_all_tap.mif            words= 11060 不符= 11060 缺 Sobel 段=  6  不一致!
仓库根 rom_all_tap.coe         words= 11060 不符= 11060 缺 Sobel 段=  6  不一致!
Vivado 工程 mem_init_files/…   words= 11060 不符= 11060 缺 Sobel 段=  6  不一致!
python/golden/rom_all_tap.hex words= 11066 不符=     0 缺 Sobel 段=  0  OK
结论：FAIL —— 权重(ROM) 和 偏置(C头文件) 不是同一套，必须重新生成 ROM
```

> 根因的制度性原因：`py/` 被 `.gitignore` 忽略（`.gitignore:16`），
> 而 ROM IP 的初始化文件正好指向 `../../../py/rom_all_tap.coe` 这个**未跟踪的本地文件**。
> 建议让 ROM 生成脚本只读**受版本管理的** `LeNet_hw/include/lenet_weights_hw.h`
> （`export_wbase_tap.py` 已经这么做了），并且约定"谁改了头文件，谁负责重新生成 IP"。
